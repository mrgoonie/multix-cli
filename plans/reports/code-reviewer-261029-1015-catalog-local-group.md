## Findings

### Critical, High, Medium
None.

### Low

1. **Group membership is listed in four separate places, and this bug came from that** (`agent-runtime.ts:47` `UNRECORDED`, `:51` `LOCAL_GROUPS`, `:76` `NON_PROVIDER_GROUPS`, `:111` `NO_DRY_RUN_GROUPS`).
   - What happened: `catalog` had been added to `UNRECORDED` but not to the other two sets. That gap is the cause of #430.
   - How it can recur: the next local group added (for example a future `scene`-style local tool) can repeat the same omission.
   - Suggested fix (not required in this PR): a unit assertion that every group matched by `UNRECORDED` is also in `NON_PROVIDER_GROUPS`, or one table that derives all four sets. Open this as a separate issue under the AGENTS.md rule; do not widen this PR.

2. **The new test covers only `catalog compare --help` and the error envelope of `catalog show`** (`tests/smoke/agent-mode.test.ts:486-496`).
   - Nested subcommands such as `catalog note add` and `catalog reviews rm` get the same result through the recursion in `addGlobalFlags`, so the coverage is adequate.
   - The test is a real check, not a placeholder: before the fix, `run.group` was `"catalog"`, so the `provider` assertion would have failed.
   - No change requested.

3. **The `billable` check now repeats itself for catalog** (`agent-runtime.ts:125`): `sendsRequests` is already false for catalog, so `!NON_PROVIDER_GROUPS.has(group)` changes nothing.
   - This redundancy existed before the PR (it is the same for `check`, `models`, `guide`, `history` and `rerun`).
   - No action.
